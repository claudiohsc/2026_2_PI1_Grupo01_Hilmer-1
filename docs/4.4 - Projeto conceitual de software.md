A documentação do _software_ deverá conter, no mínimo, os itens a seguir:

- **Diagrama BPMN para entender o software proposto:** deve deixar claro os principais atores do sistema, suas atividades (de negócios), insumos e resultados.
- **Backlog funcional do software:**
  - Escrito no formato de histórias de usuário ou casos de uso (decisão da equipe);
  - Ao declarar o backlog de requisitos funcionais, usar a classificação de MoSCoW (Must have, Should have e Could have), para um melhor entendimento do próprio backlog.
- **Backlog não-funcional do software:**
  - Descrever os requisitos não-funcionais de forma objetiva;
  - Mais facilmente, mais rapidamente, são descrições subjetivas não-válidas. Um exemplo de requisito não-funcional de desempenho: "a página deve carregar em até 5s quando em conexão 4G". 
- **Diagrama de casos de uso**, contendo os atores do sistema, os requisitos com os quais eles interagem e os tipos de relacionamentos entre requisitos realizados por um mesmo ator (ex.: include, extend). Obs.: este é um diagrama sobre requisitos funcionais.
- **Descrição da arquitetura da solução de software proposta:**
  - Propósito do software (qual o seu papel no sistema);
  - Estilo arquitetural contendo:
    - Padrão adotado: MVC, MVP, Microsserviços, Monolítico, etc (Justificar);
    - Linguagens de programação: Java, Python, C\#, JavaScript, etc.
    - Frameworks e bibliotecas: Spring Boot, .NET Core, React, Angular, Django, etc.
    - Banco de dados: Relacional (PostgreSQL, MySQL, etc) X NãoSQL (MongoDB,etc). 
  - Diagrama de alto nível: representação esquemática dos componentes da arquitetura, suas responsabilidades e comunicações, esclarecendo a composição do front-end e do back-end.
- **Persistência de dados:** diagrama de entidade relacionamento do banco de dados usado na solução proposta.
- **Análise de dados:** as variáveis definidas nos requisitos do projeto em abordagem numérica e gráfica.
- **Diagrama de estados** esclarecendo os estados assumidos pelo software e os eventos que causam as mudanças de estado do software.


## Backlog

### 1. Backlog Funcional do Software

As funcionalidades abaixo foram descritas no formato de Histórias de Usuário ("*Como [ator], eu quero [ação] para que [motivo/resultado]*") para facilitar o entendimento do valor entregue por cada item, juntamente com a sua classificação de prioridade MoSCoW.

| ID | Nome do Requisito | Prioridade | História de Usuário |
| :---: | :--- | :---: | :--- |
| **RF01** | Navegação pelo labirinto | Must have | Como sistema autônomo, eu quero percorrer o labirinto da posição inicial à final para completar o desafio proposto. |
| **RF02** | Reconhecimento de ambiente | Must have | Como sistema de percepção, eu quero identificar os diferentes elementos físicos (paredes e piso) para evitar colisões e mapear o espaço corretamente. |
| **RF03** | Construção do mapa do labirinto | Must have | Como sistema de mapeamento, eu quero construir um mapa quadriculado do labirinto baseado no percurso para reconhecer o terreno. |
| **RF04** | Armazenamento do mapa labirinto | Must have | Como sistema de controle, eu quero armazenar o mapa quadriculado do labirinto em memória para permitir o planejamento eficiente de rotas. |
| **RF05** | Localização do robô | Must have | Como robô, eu quero identificar minha posição atual (odometria) para me localizar dentro do mapa construído. |
| **RF06** | Percurso do robô | Should have | Como operador, eu quero visualizar o percurso feito pelo micromouse para analisar e validar a estratégia de exploração. |
| **RF07** | Detecção do objetivo | Must have | Como robô, eu quero detectar quando alcançar a célula de destino (canto oposto ao início) para sinalizar o fim da corrida. |
| **RF08** | Telemetria em tempo real | Must have | Como operador, eu quero visualizar dados de telemetria em tempo real para monitorar as condições e o funcionamento do robô durante o desafio. |
| **RF09** | Armazenamento em banco de dados | Must have | Como sistema, eu quero armazenar os dados de telemetria no banco de dados para permitir consultas, métricas e análises posteriores. |
| **RF10** | Consulta de todos os labirintos | Should have | Como usuário, eu quero consultar os dados de todos os labirintos já percorridos para comparar o histórico de desempenho do micromouse. |
| **RF11** | Sobrepujar condições do solo | Should have | Como robô, eu quero ser capaz de sobrepujar e compensar condições irregulares do solo para não interromper o meu percurso. |
| **RF12** | Tratamento de colisões | Must have | Como sistema de navegação, eu quero desviar proativamente das paredes para evitar colisões que danifiquem o robô ou prejudiquem o tempo. |
| **RF13** | Calibração de Hardware | Must have | Como sistema embarcado, eu quero executar uma rotina de auto-calibração dos sensores antes do deslocamento para garantir a precisão das leituras. |
| **RF14** | Dashboard de Telemetria | Must have | Como usuário, eu quero acessar um Dashboard de Telemetria com mapa bidimensional, trajeto, velocidade média e bateria para ter controle visual total sobre a operação. |
| **RF15** | Gestão de Corridas | Must have | Como sistema de gestão, eu quero registrar cada tentativa com um ID único para permitir a filtragem por tipo de labirinto (4x4, 8x4, 12x4). |
| **RF16** | Estabilização de telemetria | Must have | Como sistema de comunicação, eu quero manter um buffer de dados para não perder informações de telemetria em caso de instabilidade na conexão. |
| **RF17** | Recuperação de Impacto | Should have | Como sistema autônomo, eu quero me recuperar de colisões sem perder o mapeamento já realizado para continuar a exploração. |

### 2. Backlog Não-Funcional do Software

Os requisitos não-funcionais definem as restrições e critérios de qualidade que o sistema deve atender, descritos de forma objetiva.

| ID | Nome do Requisito | Prioridade | Descrição Objetiva |
| :---: | :--- | :---: | :--- |
| **RNF01** | Restrição de Dimensão | Must have | O robô deve possuir dimensões máximas de 16,5 cm de comprimento e largura, sem restrição de altura. |
| **RNF02** | Restrição de Locomoção | Must have | É estritamente proibido o uso de voo, salto, escalada ou propulsão por combustão/foguete para o deslocamento. |
| **RNF03** | Desempenho de Tempo | Must have | O software do robô deve ser capaz de concluir qualquer labirinto dentro do limite máximo de 10 minutos. |
| **RNF04** | Eficiência Energética | Should have | O sistema deve gerenciar o consumo para garantir autonomia de bateria suficiente para completar 3 labirintos consecutivamente. |
| **RNF05** | Desempenho de Telemetria | Should have | A interface web deve exibir as atualizações de telemetria com latência máxima de 2 segundos após a leitura dos sensores. |
| **RNF06** | Confiabilidade Mecânica | Must have | A estrutura física e montagem de componentes devem resistir a impactos e colisões de rotina sem apresentar falhas de funcionamento. |
| **RNF07** | Nível de Autonomia | Must have | A tomada de decisão e a execução do percurso devem ser 100% autônomas, sem qualquer intervenção humana externa. |
| **RNF08** | Desempenho de Hardware | Must have | A rotina de inicialização e auto-calibração mecânica/eletrônica deve ser concluída em até 1 segundo. |
| **RNF09** | Desempenho de Software | Should have | O sistema operacional e os softwares embarcados devem estar inicializados e prontos para execução em até 2 segundos. |

### 2. Mapeamento de Telas e Estados Operacionais

A interface do sistema web foi concebida para atender à supervisão de bancada e à persistência dos resultados, dividindo-se entre a visualização dinâmica de corrida e a área analítica de banco de dados:

| Identificador | Nome da Vista / Estado | Descrição Funcional | Requisitos Atendidos |
| :---: | :--- | :--- | :---: |
| `01_Idle` | Aguardando Largada | Robô alinhado na célula verde de largada ($A1$ ou $A12$), sensores e odometria sincronizados, métricas nominais zeradas e acionamento manual de início. | RF05, RF13, RNF09 |
| `02_Running` | Telemetria ao Vivo | Plotagem vetorial em tempo real da rota percorrida sobre a malha escura, atualização contínua de velocidade média, consumo de bateria e cronometragem. | RF03, RF06, RF08, RF14, RNF03, RNF05 |
| `03_Completed` | Conclusão do Desafio | Detecção de chegada ao objetivo diametralmente oposto ($D12$ ou $D1$), travamento do cronômetro, sinalização verde de `DESAFIO CUMPRIDO: SIM` e acionamento de persistência. | RF07, RF09, RNF03 |
| `04_History_View` | Consulta Consolidada | Tabela do banco de dados exibindo o histórico de todas as corridas realizadas com identificadores únicos, tempos, velocidades e status de aprovação. | RF09, RF10, RF15 |
| `04_History_View_M1..M3` | Filtros por Labirinto | Visão tabular segmentada isolando individualmente as execuções dos labirintos $4\times4$, $8\times4$ ou $12\times4$. | RF10, RF15 |

### 4. Instruções para Navegação no Protótipo

1. **Disparo da Telemetria:** No frame inicial (`01_Idle`), clique no botão primário **`INICIAR CORRIDA`** para simular o início da operação autônoma e avançar para `02_Running`.
2. **Conclusão Automática:** A partir de `02_Running`, uma transição automática (*After delay*) executa a interpolação fluida do robô completando o trajeto até a meta em `03_Completed`.
3. **Reset / Nova Tentativa:** No frame de conclusão, clique em **`RESETAR / NOVA TENTATIVA`** para retornar ao estado inicial `01_Idle` com incremento de tentativa.
4. **Consulta ao Banco de Dados:** A qualquer momento, clique na aba **`Histórico de Consultas`** no cabeçalho para abrir a visualização tabular (`04_History_View`).
5. **Filtragem de Dados:** Na tela de histórico, clique nos botões de controle segmentado (`Todos`, `Labirinto 1`, `Labirinto 2`, `Labirinto 3`) para alternar a exibição filtrada dos registros. Para voltar à bancada ao vivo, selecione a aba **`Telemetria ao Vivo`**.
